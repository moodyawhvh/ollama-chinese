有时 Ollama 的表现可能不如预期。弄清发生了什么,最好的办法之一就是查看日志。在 **Mac** 上,运行以下命令找到日志:

```shell
cat ~/.ollama/logs/server.log
```

在带 systemd 的 **Linux** 系统上,用这条命令查看日志:

```shell
journalctl -u ollama --no-pager --follow --pager-end
```

在**容器**中运行 Ollama 时,日志输出到容器的 stdout/stderr:

```shell
docker logs <container-name>
```

(用 `docker ps` 找到容器名)

如果在终端手动运行 `ollama serve`,日志会直接打印在该终端上。

在 **Windows** 上运行 Ollama 时,日志分布在几个不同位置。按 `<cmd>+R` 并输入以下命令,即可在资源管理器中查看:

- `explorer %LOCALAPPDATA%\Ollama` 查看日志。最新的服务端日志在 `server.log`,更早的日志在 `server-#.log`
- `explorer %LOCALAPPDATA%\Programs\Ollama` 浏览可执行文件(安装器会把该目录加入用户 PATH)
- `explorer %HOMEPATH%\.ollama` 浏览模型和配置的存储位置
- `explorer %TEMP%` 临时可执行文件存放在一个或多个 `ollama*` 目录中

要开启额外的调试日志来辅助排错,先**从托盘菜单退出正在运行的应用**,然后在 PowerShell 终端中执行:

```powershell
$env:OLLAMA_DEBUG="1"
& "ollama app.exe"
```

加入 [Discord](https://discord.gg/ollama),获取解读日志方面的帮助。

## LLM 运行库

Ollama 内置了多个针对不同 GPU 和 CPU 向量特性编译的 LLM 运行库。Ollama 会根据你系统的能力自动挑选最合适的一个。如果自动探测出问题,或你遇到其他问题(例如 GPU 崩溃),可以通过强制指定某个 LLM 运行库来绕过。`cpu_avx2` 性能最好,其次是 `cpu_avx`,最慢但兼容性最好的是 `cpu`。macOS 上的 Rosetta 转译只能配合 `cpu` 运行库工作。

在服务端日志中,你会看到类似这样的信息(不同版本有所差异):

```
Dynamic LLM libraries [rocm_v6 cpu cpu_avx cpu_avx2 cuda_v11 rocm_v5]
```

**实验性:覆盖 LLM 运行库**

你可以把 OLLAMA_LLM_LIBRARY 设置为任意可用的 LLM 运行库来绕过自动探测。例如,你有一块 CUDA 显卡,但想强制使用支持 AVX2 向量指令的 CPU 运行库:

```shell
OLLAMA_LLM_LIBRARY="cpu_avx2" ollama serve
```

你可以用下面的命令查看你的 CPU 支持哪些特性。

```shell
cat /proc/cpuinfo| grep flags | head -1
```

## 在 Linux 上安装旧版本或预发布版本

如果你在 Linux 上遇到问题想安装旧版本,或者想在正式发布前试用预发布版本,可以告诉安装脚本要安装的版本。

```shell
curl -fsSL https://ollama.com/install.sh | OLLAMA_VERSION=0.5.7 sh
```

## Linux tmp 目录 noexec

如果你的系统对 Ollama 存放临时可执行文件的目录设置了 "noexec" 标志,可以通过设置 OLLAMA_TMPDIR 指定一个 ollama 运行用户可写的替代位置。例如 OLLAMA_TMPDIR=/usr/share/ollama/

## Linux docker

如果 Ollama 在 docker 容器里起初能用 GPU,但运行一段时间后切换到 CPU,且服务端日志报 GPU 发现失败,可以通过在 Docker 中禁用 systemd cgroup 管理来解决。编辑宿主机上的 `/etc/docker/daemon.json`,在 docker 配置中加入 `"exec-opts": ["native.cgroupdriver=cgroupfs"]`。

## NVIDIA GPU 发现

Ollama 启动时会盘点系统中的 GPU,以确定兼容性和可用显存大小。有时这一发现过程可能找不到你的 GPU。一般来说,使用最新驱动效果最好。

### Linux NVIDIA 排查

如果你用容器运行 Ollama,请先按 [docker](./docker) 文档配置好容器运行时。

有时 Ollama 初始化 GPU 会失败。检查服务端日志时,会看到各种错误码,例如 "3"(未初始化)、"46"(设备不可用)、"100"(无设备)、"999"(未知)等。以下排查手段可能有助于解决问题:

- 如果你在用容器,容器运行时正常吗?试试 `docker run --gpus all ubuntu nvidia-smi`——如果这条命令不行,Ollama 也无法看到你的 NVIDIA GPU。
- uvm 驱动加载了吗?`sudo nvidia-modprobe -u`
- 尝试重新加载 nvidia_uvm 驱动——先 `sudo rmmod nvidia_uvm`,再 `sudo modprobe nvidia_uvm`
- 尝试重启机器
- 确保你运行的是最新的 nvidia 驱动

如果以上都无法解决问题,请收集更多信息并提交 issue:

- 设置 `CUDA_ERROR_LEVEL=50` 后重试,获取更多诊断日志
- 检查 dmesg 中的报错 `sudo dmesg | grep -i nvrm` 和 `sudo dmesg | grep -i nvidia`

## AMD GPU 发现

在 Linux 上,访问 AMD GPU 通常需要把用户加入 `video` 和/或 `render` 组,才能访问 `/dev/kfd` 设备。如果权限配置不正确,Ollama 会检测到这一点并在服务端日志中报错。

在容器中运行时,部分 Linux 发行版和容器运行环境下,ollama 进程可能无法访问 GPU。在宿主机上执行 `ls -lnd /dev/kfd /dev/dri /dev/dri/*` 确定你系统上的**数字型**组 ID,然后向容器传入额外的 `--group-add ...` 参数,让它能访问所需设备。例如,在输出 `crw-rw---- 1 0  44 226,   0 Sep 16 16:55 /dev/dri/card0` 中,组 ID 列是 `44`。

如果你无法让 Ollama 正确发现或使用 GPU 进行推理,以下手段可能帮助定位故障:

- `AMD_LOG_LEVEL=3` 开启 AMD HIP/ROCm 库的信息级日志。这能展示更详细的错误码,有助于排错
- `OLLAMA_DEBUG=1` GPU 发现期间会上报额外信息
- 检查 dmesg 中 amdgpu 或 kfd 驱动的报错 `sudo dmesg | grep -i amdgpu` 和 `sudo dmesg | grep -i kfd`

### AMD 驱动版本不匹配

如果你的 AMD GPU 在 Linux 上未被检测到,且服务端日志出现类似这样的信息:

```
msg="failure during GPU discovery" ... error="failed to finish discovery before timeout"
msg="bootstrap discovery took" duration=30s ...
```

这通常说明系统的 AMD GPU 驱动太旧。Ollama 捆绑的 ROCm 7 Linux 库需要配套的 ROCm 7 内核驱动。如果系统运行的是更老的驱动(ROCm 6.x 或更早),GPU 初始化会在设备发现阶段卡住并最终超时,导致 Ollama 回退到 CPU。

解决办法:使用 [AMD ROCm 文档](https://rocm.docs.amd.com/projects/install-on-linux/en/latest/)中的 `amdgpu-install` 工具升级到 ROCm v7 驱动。升级后重启系统并重新启动 Ollama。

如果在 Linux 上模型跨多块 AMD GPU 加载时出现乱码回复,请参阅以下指南。

## Windows 终端乱码

较老版本的 Windows 10(例如 21H1)存在一个已知 bug:标准终端程序无法正确显示控制字符。这会导致屏幕上出现一长串类似 `←[?25h←[?25l` 的字符,有时还会报 `The parameter is incorrect` 错误。解决办法是升级到 Win 10 22H2 或更新版本。
